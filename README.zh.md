# 一个线程缓存式内存分配器

C++14 实现的三层内存分配器,对照 **5 个基线分配器 × 3 个操作系统** 做了完整测量。

它的设计只有一个核心决定 —— **每个线程一份私有缓存,并且几乎从不把内存还给操作系统** —— 而下面所有的优势和劣势,都是这一个决定的两面。

| | |
|---|---|
| 每次调用成本 | **2.67 ns**,对 libmalloc 的 4.94 ns(单线程,16 字节)|
| 最好的负载 | `ramp/bulk` **4.51×**(Windows 上 9.52×)|
| 最差的负载 | `large/interleaved` **0.047×** —— 8 线程时 0.02× |
| 峰值内存 | libmalloc 的 **22.5×**,应用活跃数据的 **214×** |
| p99.9 尾延迟 | libmalloc 的 **11.2×** |
| 对真正的同类 | Linux 上 tcmalloc 比它快 **2.7×**,同时只占五分之一内存 |

最后两行是重点。这不是一个「我实现了 tcmalloc 而且它很快」的项目,而是一个把**简化的代价逐项标价**的项目。

---

## 1. 结构

三层。一次分配由能满足它的最浅那一层服务,只有最深那一层会向操作系统要内存。

```mermaid
flowchart LR
    APP["应用<br/>ConcurrentAlloc(n)"]

    subgraph L1["ThreadCache — 每线程一份,无锁"]
        TC["208 条 size-class 自由链表"]
    end

    subgraph L2["CentralCache — 共享,每个 size class 一把锁"]
        CC["每个 size class 一组 span"]
    end

    subgraph L3["PageCache — 共享,一把全局锁"]
        PC["空闲 span,1..128 页<br/>合并相邻块"]
    end

    OS["操作系统<br/>mmap / VirtualAlloc"]

    APP -->|"&le; 256 KB"| TC
    TC -->|"链表空:<br/>批量取一把"| CC
    CC -->|"没有 span:<br/>切一片新的"| PC
    PC -->|"8 KB 页"| OS
    APP -->|"&gt; 256 KB"| PC
```

| 层 | 作用域 | 同步 | 职责 |
|---|---|---|---|
| `ThreadCache` | 每线程 | **无** | 从自由链表 pop/push。这是全部意义所在。 |
| `CentralCache` | 全局 | 每个 size class **一把**互斥锁 | 从 span 切出对象,成批交出。 |
| `PageCache` | 全局 | **一把**全局互斥锁 | 向 OS 要页,切分与合并 span。 |

分层是快路径无锁的原因:一个线程只有在自己的链表耗尽时才会碰到共享状态,而一旦碰到,它就取足够多的对象来摊薄这次往返。

**注意最后那条边** —— `> 256 KB` 直接落到 `PageCache` 的全局锁上,完全绕过线程缓存。这条边是本项目最大的一处劣势,第 6 节会回来算账。

### size class 与 page map

请求尺寸被向上取整到 **208 个 size class**(≤128 字节按 8 对齐,≤1 KB 按 16,≤8 KB 按 128,以此类推)。对齐粒度是一个真实的设计旋钮 —— 第 6 节末尾有一个改动它的实验。

释放时只有一个指针,所以必须能从**指针反查它所属的 span**。这靠一张三层基数树(page map)完成:页号 = 地址 >> 13,12/12/11 位分三级,节点惰性分配、每个 16–32 KB。读路径不加锁(节点一旦发布就永不释放,靠 acquire/release 配对保证可见性),因为它在每一次 `free` 上。

### 一个移植 bug,以及它为什么值得写出来

这个项目最初是 32 位 Windows 构建。移到 64 位时做了显而易见的那些改动(`mmap` 换 `VirtualAlloc`、`thread_local` 换 `__declspec(thread)`、64 位的 `PAGE_ID`),然后**在第一次 `free` 上就段错误了**。

page map 原本是一个 `2^19` 项的平坦数组 —— 覆盖地址空间最低的 **4 GB**。在 32 位构建里那就是全部地址空间;在 64 位主机上 `mmap` 返回远高于 4 GB 的地址,于是**每一个合法指针的页号都越界**,查表返回空,第一次释放就解引用它。

修法就是真 tcmalloc 的做法:让树的深度跟随地址空间宽度。而这引出第二个 bug —— 两级split会让每个叶子节点 2 MB,而 `ObjectPool` 以固定 128 KB 分块补货,**会毫无怨言地从 128 KB 的块里交出一个 2 MB 的对象**。所以最终是三级。

另外两个也值得记:

- `FetchFromCentralCache` 在批量返回为空时**从非 void 函数尾部掉出去**。一个 `assert` 在 debug 构建里盖住了它,在 `-DNDEBUG` 下消失 —— 也就是说,**未定义行为恰好只存在于你用来跑基准的那个配置里**。
- 头文件被包含在其模板所依赖的声明之前。MSVC 接受,clang 和 GCC 正确地拒绝。

细节见 BENCHMARKS.md 的 P 节。

## 2. 一次分配怎么走

**快路径(≤ 256 KB,约 95–99% 的调用):**

1. 读线程局部的 `ThreadCache` 指针
2. 把请求尺寸算成 size class 下标
3. 如果那条链表非空 —— `pop`,返回

没有原子操作,没有锁,没有系统调用。反汇编下来大约十几条指令。

**掉出快路径时,代价是级联的:**

链表空 → 取 `CentralCache` 里该 size class 的锁 → 若没有可用 span,再取 `PageCache` 的全局锁 → 若没有合适的空闲 span,`mmap` 一片新的。

一次本地 `pop` 约 **2 ns**,一次到 `CentralCache` 的往返约 **70 ns** —— 差 35 倍。所以「快路径命中率」不是一个装饰性指标,它就是性能本身。取回时会一次取一批(批量大小随该 size class 的使用逐次 +1,慢启动),用来摊薄往返成本。

**> 256 KB 的路径完全不同:** 直接取 `PageCache` 全局锁,直接 `mmap`。没有缓存,没有批量,没有per-thread 任何东西。

## 3. 一次释放怎么走

`ConcurrentFree(void* ptr)` **只接受指针** —— 不要求调用者记住尺寸。所以第一步必须是 page map 反查:指针 → span → `span->_objSize`。

拿到尺寸之后:

1. 若 > 256 KB —— 取 `PageCache` 全局锁,整片 span 退回
2. 否则 push 回本线程对应的链表
3. 如果这条链表长度超过它的上限,把一批**还给** `CentralCache`
4. 一个 span 上所有对象都归还后,span 退回 `PageCache`,并与相邻的空闲 span 合并

**关键在于第 5 步不存在:** `PageCache` 只有在一个 span 达到 128 页(1 MB)时才会 `munmap`。对一个所有对象都 ≤ 8 KB 的负载,**什么都不会还给操作系统**。峰值内存因此变成进程生命期内的高水位。

这是一个刻意的选择,不是遗漏 —— 它是第 6 节里最大的胜场和最大的内存代价的**同一个来源**。

## 4. 怎么测的

自带一个 harness(`main.cpp`),同一个进程里交替跑两个分配器,可调线程数、轮数、尺寸分布、访问模式,并单独报告峰值 RSS、次缺页、以及逐次调用的延迟分位数。

**尺寸分布** `fixed`(16 字节) `ramp`(1 B–8 KB 顺序递增) `random`(同区间随机) `classstep`(每次落在不同 size class) `large`(> 256 KB)
**访问模式** `bulk`(全部分配再全部释放) `interleaved`(固定 64 个活跃对象的滚动窗口) `cross`(线程 N 释放线程 N+1 分配的内存)

**对照的 5 个基线 × 3 个 OS:** Windows UCRT、macOS libmalloc、glibc ptmalloc、mimalloc、真正的 gperftools tcmalloc。

### 正确性门,以及为什么 ASan 不够

一个只报性能、不说怎么验正确性的 README 是可疑的。这里的门是 `verify.cpp`:它在每个块里写入可校验的印记,并统计四类失败 —— 返回空、未对齐、印记被破坏(说明块被重复交出或过短)、重复释放。

**而 AddressSanitizer 在这里几乎无用。** 一个自定义分配器的自由链表对 ASan 是不透明的(全项目零处 `ASAN_POISON` 标注),所以它看不进去。实测:在一个故意做坏的分配器上,**ASan 报 0 个错误,`verify.cpp` 抓到 12 处**。

门本身也要验:`--alloc broken` 必须 FAIL(否则这个门是假的)。

### 三条方法学纪律

- **单次测量不可信**(本机 ±25%)。所有头条数字取 **≥5 次独立进程的中位数**,并报区间。
- **内存必须一个分配器一个进程测。** `ru_maxrss` / `PeakWorkingSet` 是进程级的单调高水位,两个分配器在一个进程里测毫无意义。
- **换分配器后必须做正向验证。** 三个平台各有一种**静默失败**:macOS 上链接 `-ltcmalloc` 会静默接管 `malloc`;Linux 上 `--as-needed` 会静默丢掉库;Windows 上静态 CRT(`/MT`)会让注入"成功"但全部调用仍走 CRT。这三个陷阱每一个都曾让一整批数据变成测了别的东西。

## 5. 结果

macOS 数据为 Apple M3 Pro / macOS 15,4 线程,15 次独立进程中位数。Linux 为 4 核 Ubuntu 22.04 aarch64,Windows 为 Ryzen 7 7700X / Win10 x64。完整逐节记录见 BENCHMARKS.md。

### 5.1 对系统分配器

`> 1` 表示这个分配器更快。

| 负载 | Windows UCRT | macOS libmalloc | glibc ptmalloc |
|---|---|---|---|
| `ramp/bulk` | **9.52×** | **4.51×** | **5.10×** |
| `classstep/interleaved` | **22.82×** | **3.80×** | **9.38×** |
| `random/interleaved` | — | **3.21×** | — |
| `fixed/interleaved` | **2.59×** | **1.47×** | 0.63× |
| `ramp/interleaved` | **1.77×** | 0.83× | **1.14×** |
| `fixed/bulk` | **1.35×** | 0.35× | 0.30× |
| `large/interleaved` | — | **0.047×** | — |

### 5.2 对现代同类

| 负载 | mimalloc (Win) | 真 tcmalloc |
|---|---|---|
| `ramp/bulk` | 1.01×(平手) | **1.43×** |
| `classstep/interleaved` | 0.91× | 0.74× |
| `fixed/interleaved` | 0.57× | 0.72× |
| `ramp/interleaved` | 0.49× | 0.41× |
| `fixed/bulk` | 0.24× | 0.45× |

**胜场随基线质量下降:** Windows UCRT **5/5** → macOS libmalloc **3/5** → glibc **3/5** → mimalloc **1/5** → 真 tcmalloc **1/5**(而且那唯一一场 1.01× 是平手)。

对 UCRT 全胜说明的是 UCRT 的位置,不是这个分配器的。那个 **22.82×** 是整个项目里信息量最低的一个数字 —— 换个基线它变成 0.74×。

### 5.3 跨平台的位置,比跨负载的位置更稳

这是最锋利的一条结论:

| | 同一负载在不同 OS 之间摆动 |
|---|---|
| 对**系统** malloc | 中位 **2.4×**(最高 4.5×) |
| 对**同一份**真 tcmalloc | **1.3×** |

而 `classstep/interleaved` 对真 tcmalloc 在 **Linux 和 Windows 上都恰好是 0.74×**。

**方差从来不在这个分配器这一边** —— 它在「各家系统 malloc 彼此差多远」这件事上。

### 5.4 内存 —— 最严重的缺陷

峰值 RSS,一个分配器一个进程:

| 负载 | 本分配器 | libmalloc | 倍数 |
|---|---|---|---|
| `fixed/interleaved` | 3.0 MB | 2.9 MB | 1.0× |
| `ramp/bulk` | 252 MB | 123 MB | 2.1× |
| `random/interleaved` | 72 MB | 11 MB | 6.5× |
| `classstep/interleaved` | 91 MB | 7.9 MB | 11.6× |
| **`ramp/interleaved`** | **186 MB** | **8.3 MB** | **22.5×** |

那最后一行里,**应用真正在用的活跃数据是 0.87 MB** —— libmalloc 持有它的 9 倍,这个分配器持有 **214 倍**。而真 tcmalloc 在 Linux 上做等量的工作只持有 22 MB,**同时更快**。

**不是 size class 取整浪费造成的** —— 那只有 1.5%、约 0.04 MB。真正的四个成因:

1. **自由链表只增不减。** 容量上限每次补货 +1,代码里**没有任何一处**减小它。一个负载在某次突发里碰过一次的 size class,会把容量保持到进程结束。
2. **一个活对象钉住整片 span。** span 只在其 `_useCount` 归零时才退回。约 130 个活跃 size class 各持有一片 31–32 页(约 250 KB)的 span、每片上还有几个对象没还,钉住的总量就是几十 MB。
3. **`PageCache` 几乎从不归还。** 只有 128 页以上的 span 才会走到 `munmap`。
4. **size class 的数量本身**(见 5.6)。

### 5.5 尾延迟

逐次调用采样(约每 16 次采一次,随机化步长以免与周期性慢路径混叠),`ramp/interleaved`:

| | p99 | p99.9 |
|---|---|---|
| 本分配器 | 361 ns | **2 631 ns** |
| libmalloc | 70 ns | **235 ns** |

**尾延迟不是一项独立的优势,它跟快路径命中率走。** 在快路径命中的负载上(`random/interleaved`)尾部反而更好;一旦掉出去,就是一个数量级。慢路径在这里是级联的 —— 链表空、然后 `CentralCache` 锁、然后 `PageCache` 锁、然后可能一次 `mmap` —— 而递增尺寸的负载会持续地触发它。

### 5.6 那唯一的一场输,是一个常数而不是设计

`ramp/interleaved`(递增尺寸 + 有界活跃集)是唯一输给 libmalloc 的负载。诊断分两半,各占一半:

**我们这一半:** 递增尺寸让每个 size class 进入「排空 → 积压」的循环,堆积量约 64 个对象撞上约 19 的容量上限装不下,于是 **每千次分配 87 次 `CentralCache` 往返**(随机尺寸只有 18)。

**libmalloc 那一半:** 用 `malloc_size()` 实测,1 KB 到 8 KB 这一段 —— 也就是这个负载 87% 的范围 —— **它量化到 512 字节,我们量化到 128**。它的桶粗 4 倍,斜坡在每个桶里停留 4 倍长,同样的惩罚被摊到 4 倍多的分配上。

**于是把我们的粒度改成它的:**

| | 128 字节 | 512 字节 |
|---|---|---|
| `ramp/interleaved` | 0.80× [0.64–0.90] | **1.26× [1.12–1.43]** |
| 它的峰值内存 | 186 MB(22.5×) | **80 MB(9.7×)** |
| 它的 p99.9 | 2 631 ns | **528 ns** |
| `CentralCache` 往返/千次 | 87 | 50 |
| 代价:`ramp/bulk` / `ramp/cross` | 4.46× / 2.52× | **3.39× / 1.89×** |

两个区间不重叠。这是三次干预尝试里**唯一净收益为正**的一次,而它最强的证据不是结果本身 —— 是 BENCHMARKS.md 的 E 节在**这个配置存在之前**拟合出的成本模型(每次分配 2 ns + 每次往返 70 ns),对干预后的时间**预测到 +4.6%**。

代价的机制也定住了:类数少 4 倍,每个类持有 4 倍的活跃对象,于是 span 更容易完全排空、退回 `PageCache`、下一轮被重新切分。**回收是内存下降的原因,重新切分是 `bulk` 变慢的原因** —— 同一件事。

改动以编译期开关 `-DMID_ALIGN_SHIFT=9` 提供,**默认关闭**(项目里其余所有数字都是在 128 下测的)。详见 BENCHMARKS.md 的 W 节。

## 6. 数据说明了什么

### 核心权衡

**一个从不归还内存的 per-thread 缓存。** 下面五个结果全部来自这一个决定:

| 这个决定的一面 | 结果 |
|---|---|
| 快路径短 | 每次调用便宜 1.85× ✅ |
| 从不归还 → 页不用重新 fault | `bulk` 类负载大胜 4.5–9.5× ✅ |
| 从不归还 → 高水位就是峰值 | 内存 22.5× ❌ |
| 缓存未命中要级联 | p99.9 差 11.2× ❌ |
| 缓存需要预热 | 冷启动惩罚 3× ❌ |

优势和劣势不是两张清单,是同一个权衡的两面。这一点在 `ramp/bulk` 上最锋利:**囤积在那儿赢 4.5×,在 `ramp/interleaved` 上输 22.5× 内存 —— 同一个策略,同一份代码,什么都没改。**

### 优势

**① 快是因为快路径短,不是因为免锁。**

单线程实测 **2.67 ns 对 4.94 ns = 1.85×**。而且这个优势**在单线程时最大,随并发单调衰减**:

| 线程 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| 倍数 | **3.04×** | 2.62× | 2.26× | **1.82×** |

这和「无锁设计在竞争下取胜」的故事**恰好相反**。免锁是这个结构的副产品,不是收益来源。

⚠️ 而且必须诚实:逐项排除后 —— 原子指令(免费)、一把真 mutex(比整个差距还大,所以不可能)、zone 分派(测不动)、`malloc(0)`/`free(NULL)`/自由链表校验这类契约工作(全部在噪声底以下)—— **约 2 ns 仍然无法归因**。优势是真的且可复现,机制只解释了三分之一。

**② 不归还内存是一种吞吐策略,而且有效。**

`bulk` 类负载的大胜**不是分配速度,是缺页**。每千次操作的次缺页:

| | 本分配器 | libmalloc | glibc |
|---|---|---|---|
| `ramp/bulk` | **9.3** | 223 | **642** |

对手把内存还给了 OS,于是下一轮要重新 fault 进来。这个分配器不还,所以不用。**同一个策略,在 5.4 节里要付 22.5× 的账。**

**③ 优势的大小是对手的属性,不是自己的。**

见 5.2。胜场从 5/5 单调掉到 1/5。任何单一基线上的数字都主要在描述那个基线。

### 劣势

**① 囤积。** 22.5× 峰值内存,活跃集的 214×。四个成因,没有一个是块内碎片。修法不是停止囤积,而是加一个 scavenger —— 真 tcmalloc 就是这么做的,它拿 22 MB 还更快。而一次「提高缓存容量但不加回收」的尝试让**两个指标都变差**(BENCHMARKS.md O 节),这是同一个教训的另一个方向。

**② 没有快路径的地方,锁就是一切。**

超过 256 KB 完全没有线程缓存 —— 每次分配和释放都要拿同一把 `PageCache` 全局锁。代价随线程数**平方级**恶化:

| 线程 | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| `large/interleaved` | 0.52× | 0.15× | **0.04×** | **0.02×** |

同一个负载在**单线程**下是 2.34× 的**胜场**(`large/bulk`)—— 所以慢的不是分配逻辑,纯粹是锁竞争崩塌。

**这和优势①合起来才是关于锁的完整结论:锁确实极其重要 —— 但只在这个设计唯一忘记放缓存的地方。**

**③ 尾延迟跟着快路径走。** p99.9 差 11.2×。没有独立的「更可预测」这个性质可以主张。

**④ 冷启动惩罚 3×。** `--warmup 0` 下是 0.32×。缓存要预热;短命进程永远等不到。

**⑤ 对真正的同类会输。** Linux 上真 tcmalloc 在 `ramp/interleaved` 上跑 **1.60 ms**,这个分配器 4.33 ms,glibc 7.50 ms。**它比我们快 2.7 倍,同时只占五分之一内存。** 核心思路(线程本地链表、慢启动批量、每 size class 一把锁、span 合并、页到 span 的映射)都是对的;差距是简化的价格,而这个价格现在被标出来了。

## 7. 什么时候用它,什么时候不用

| 用它 | 用系统 malloc |
|---|---|
| 长命进程,3× 冷启动能被摊薄 | 短命进程 —— CLI 工具、测试跑器永远付不完冷启动 |
| 内存充裕,能吃下 22× 常驻 | 内存受限 —— 单这一条就足以否决 |
| 活跃集大且循环:分配一批、全部释放、重复 | 活跃集有界且尺寸顺序推进 |
| 所有对象 ≤ 256 KB | 有大于 256 KB 的分配,尤其是多线程 |
| 热循环由分配主导 | 分配之间有真实工作 —— 1 ns 的差距会消失在里面 |
| 能显式调用 `ConcurrentAlloc`/`ConcurrentFree` | 需要真正的 `malloc` 契约 |

**诚实的底线:生产环境里两个都不会选。** 每次调用的优势是一个约 2 ns 操作上的 1.85× —— 大约 **1 纳秒**,任何分配之间的真实工作都会把它盖掉。而真 tcmalloc 在 Linux 上同时打败这两个,mimalloc 在 Windows 上 5 个负载里赢 4 个,并且它们都是真正的 drop-in 替代品。

这个对比的价值不是一个部署决定,而是:**「每线程缓存 + 从不归还内存」这个权衡的代价,现在两边都被量化了 —— 大约 1 纳秒和每次调用省下的一次缺页,换来 22× 内存、11× 尾延迟、3× 冷启动,以及超过 256 KB 时的平方级崩塌。**

---

## 8. 局限

课程项目,不是一个可用的分配器:

- **不是 `malloc` 替代品。** 显式调用 `ConcurrentAlloc`/`ConcurrentFree`,没有 `operator new` 覆盖、没有 `LD_PRELOAD` shim,也没有 `realloc`/`calloc`/`posix_memalign`/`malloc_usable_size`。
- **`ConcurrentAlloc(0)` 会崩。** `Index(0)` 因下溢返回 `SIZE_MAX`,越界访问自由链表数组。断言构建能抓到,`-DNDEBUG` 构建直接崩。**已知缺陷,未修。**
- **对齐保证只有 8 字节。** 不支持过度对齐类型。
- **内存基本不归还 OS** —— 只有 128 页以上的 span。5.4 节是其后果。
- **超过 256 KB 没有任何缓存。** 劣势②是其后果。
- **没有单元测试。** 正确性靠 `verify.cpp` 和断言构建跨负载矩阵检查,这不等于一个测试套件。
- **page map 的无锁读之所以安全,只是因为节点永不释放。** 加入回收需要真正的内存序工作或 hazard pointer。
- **5 个基线、3 个平台,仍然不够。** jemalloc 未测。**现代 google/tcmalloc 的 per-CPU 缓存**(restartable sequences)—— 也就是这份文档反复引用为内存问题解法的那个机制 —— **没有测过**:它需要 Bazel 且仅限 Linux。
- **`cross` 和 `large` 的部分配置只有单次或少量测量。**

## 9. 怎么跑

```bash
c++ -std=c++14 -O2 -DNDEBUG -pthread -o bench \
    main.cpp CentralCache.cpp PageCache.cpp ThreadCache.cpp
```

**先过正确性门,再看时间:**

```bash
c++ -std=c++14 -O2 -DNDEBUG -pthread -o verify \
    verify.cpp CentralCache.cpp PageCache.cpp ThreadCache.cpp
./verify --alloc mine   --all    # 必须全部 PASS
./verify --alloc broken --all    # 必须 FAIL,否则这个门是假的
```

```bash
./bench --help
./bench --threads 4 --size ramp --pattern bulk --reps 15
./bench --size ramp --pattern interleaved --only mine     # 单独测峰值 RSS
./bench --latency --lat-stride 16 --size ramp --pattern interleaved
```

| 编译期开关 | 作用 |
|---|---|
| `-DALLOC_STATS` | 内部计数器 —— 快路径命中率、往返次数、冲刷次数、span 切分次数 |
| `-DMID_ALIGN_SHIFT=9` | 1 KB–8 KB 的 size class 改用 512 字节对齐(见 5.6)。默认关闭 |

⚠️ **在 macOS 上测量前先检查 `MallocNanoZone`。** 如果它被设成 `0`(某些工具链环境会这么做),libmalloc 面向小分配的 nano 前端会被关掉,基线在 16 字节量级上会慢 1.4–2.2 倍。用 `env -u MallocNanoZone` 得到真实默认行为。
